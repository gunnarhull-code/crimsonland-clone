## Question

Graduated from the map's "Not yet specified" fog, now that every gameplay system has a resolved design: design the Godot scene/node structure for the MVP.

- What are the top-level scenes (Arena, Player, Enemy, Weapon/Projectile, level-up UI, results screen) and how do they compose?
- Per [16 - Multiplayer-readiness architecture](16-multiplayer-readiness-architecture.md): Player is an instanced scene (not a singleton), Autoloads are reserved for genuinely global systems (enemy spawner, session/game clock, audio) — what actually goes in those Autoloads, and what's a regular instanced node?
- How do `perks.csv` and `weapons.csv` get loaded (on game start into an in-memory table both the perk-effect system and weapon system read), and where does that loading logic live?
- How is a single Enemy scene parameterized per Species/Boss Variant ([05](05-enemy-roster.md), [10](10-enemy-ai-parameters.md), [15](15-enemy-combat-stats.md)) — one Enemy.tscn with exported per-species data, or a base scene with per-species inherited scenes?

## Answer

Verified against docs.godotengine.org before locking in, per the standing instruction to always check rather than assume:

**Godot version**: **Godot 4.x** (currently the 4.7.x stable line) — the official docs explicitly recommend 4.x for new projects over 3.x. This matters concretely: Godot 4 renamed `File`/`Directory` to `FileAccess`/`DirAccess` with a different API shape (`open()` is static, no `close()`), which the CSV-loading point below depends on. Confirmed via the [release policy docs](https://docs.godotengine.org/en/stable/about/release_policy.html).

**Scene composition** (Arena.tscn root, instanced Player, Enemies/Projectiles containers, CanvasLayer UI): **confirmed**. Instancing is documented as Godot's core design language, with "quickly instance several enemies or bullets" given as the docs' own example ([Creating instances](https://docs.godotengine.org/en/stable/getting_started/step_by_step/instancing.html)). CanvasLayer is exactly the documented mechanism for a HUD/score display that doesn't scroll or scale with the game-world camera ([Canvas layers](https://docs.godotengine.org/en/stable/tutorials/2d/canvas_layers.html)) — feeds directly into [20](20-score-display.md)'s live HUD.

**Autoloads** (EnemySpawner, SessionClock, AudioManager, DataTables): confirmed as a real, documented mechanism ([Singletons (Autoload)](https://docs.godotengine.org/en/stable/tutorials/scripting/singletons_autoload.html)), but Godot's docs carry a dedicated anti-pattern warning worth citing directly: [Autoloads versus regular nodes](https://docs.godotengine.org/en/stable/tutorials/best_practices/autoloads_versus_regular_nodes.html) warns against autoloads that reach into and mutate *other* systems' state (centralized failure risk, hard-to-trace bugs). All four Autoloads here are self-contained — they track their own data and expose it, never reach into Player/Enemy internals directly — consistent with the docs' own rule of thumb, and consistent with [16](16-multiplayer-readiness-architecture.md)'s ADR already keeping Player/Enemy state off Autoloads entirely.

**CSV data loading via `FileAccess.get_csv_line()`**: real and documented ([FileAccess class reference](https://docs.godotengine.org/en/stable/classes/class_fileaccess.html)) — but correction from the original draft: Godot's docs don't actually endorse CSV as *the* recommended data-table format over `Resource`/JSON; no official page picks a winner. CSV stays the right call here anyway, for a reason specific to this project rather than a Godot recommendation: it's the one format the user can open and edit directly in a spreadsheet app, which was the explicit requirement behind `perks.csv`/`weapons.csv`/`enemies.csv` from the start. `Resource`/JSON would be more "Godot-native" but neither is spreadsheet-editable.

**Enemy scene parameterization** (one base `Enemy.tscn`, exported per-species data pulled from a new `enemies.csv`, over per-species inherited scenes): correction — this is a **community convention, not an official Godot recommendation**. Godot's own docs admit scene inheritance itself is under-documented ([open docs issue](https://github.com/godotengine/godot-docs/issues/5529)), so there's no authoritative page to cite either way. Keeping the single-scene-plus-data approach anyway, on its own merits: simpler, avoids scene inheritance's known editor-sync quirks, and it's the same pattern already established for `perks.csv`/`weapons.csv` (one generic system reading per-row data, not per-row bespoke scenes/scripts).

Materialized as [enemies.csv](../enemies.csv) — required deriving actual absolute speed numbers, since [10](10-enemy-ai-parameters.md) only ever fixed wander speed as a *percentage* of chase speed, never an absolute value (Rat 160px/s chase, Spider 220px/s burst chase, Alien 90px/s chase; wander speeds and Boss Variant rows derived from those and the ratios/multipliers already set in [10](10-enemy-ai-parameters.md)/[15](15-enemy-combat-stats.md)). `hitbox_radius_px` is left blank pending [19](19-placeholder-presentation.md). The wander-variant *shapes* (Loop/Figure-eight/Skitter-pause etc.) stay as per-species code logic keyed by `species` id, not CSV columns — they're movement algorithms, not tunable scalars, so forcing them into flat cells would fight the format rather than use it.
